## 0. 结论速览

| 问题 | 结论 | 关键证据 |
| --- | --- | --- |
| 1. 字段一致性 | **`latest_price/open/high/low` 与 baostock 不复权 `close/open/high/low` 逐位完全相同**：4 个字段各 5,213 对 / 5,212 对，**偏差恒为 0（不是"1 分以内"，是 float4 相等），0 例外** | §2；两侧列都是 `real`，同一十进制值→同一 4 字节浮点 |
| 2. 停牌票 | baostock 当日 13 只 `tradestatus=0`，其中 **12 只在快照里是"行在、价格字段全 NULL、`pre_close`=停牌前收盘"**，1 只（688496）是"有价无 OHLC 的冻结价"。**能区分"停牌"与"行缺失"，但单看 NULL 不能区分停牌 / 已退市 / 未上市** | §3 |
| 3. 北交所 | 快照含 **361 行北交所**（355×`920xxx` + 6 只旧码），**349 只有价（全部 `920xxx`）**，字段与沪深同构；腾讯 K 线 2/2 样本（920438、920001）**开高低收逐位相同** | §4；P1/P2 实测，P3（920162）0 根 bar 反证"未上市=无价" |
| 4. 收盘稳定性 | 写入时点**可回溯**：5,923 行 `created_at` 全等 `2026-10-13 16:15:54.371644`，同一次运行 2 秒前（16:15:52.5）刚写过 `stock_list` → **收盘后 +75min 的批量落库**。但该次运行的 `collection_log` 台账**不存在**（台账最早 2026-10-19），请求时刻只能由 OHLC 全等反证 | §5 |
| 5. 覆盖率 | **5,923 / 5,924 = 99.98%**，唯一缺码 `920306`（2026-10-30 才进 `stock_list`、三张表零行）→ **当日可选域 100% 覆盖**；但"可选域"不是清单驱动的（343 只已退市垃圾码来自上游） | §6 |
| **总判定** | **能作"当日 raw OHLC"的补充/核对源（单日、收盘后、沪深京全覆盖），不能作 `pre_close`/`change_percent` 的 raw 源（除权参考价口径），不能作历史回补源（只有一天、且端点无历史参数）** | §9 |

一句话：**收盘后那一次批量快照的"价格四元组"是当日真收盘，可信；但它的"昨收/涨跌幅"
是除权参考价口径，且这张表在库里只有 2026-10-13 一天、源头（efinance）已退役。**

## 1. 数据集与一条前提更正

issue 题面把 `market_snapshot` 描述为"腾讯批量报价落库"。**库内数据不是腾讯写的**：

```sql
SELECT source, count(*) FROM market_snapshot GROUP BY 1;   -- efinance | 5923
```

5,923 行**全部** `source='efinance'`（东财 `clist` 全市场快照，`efinance_adapter.py`
已于 commit `990b5fa`（#121）退役并从 `src/` 删除）。当前生产快照链是
腾讯批量报价 → 腾讯 rank → 新浪直连（`adapters/__init__.py:75-88`），**腾讯链路从未在本库
留下一整天的 snapshot 行**。

的同口径行为（停牌行形态、NULL 语义、`amplitude`/`pb_ratio` 是否填）仍需另一天实测**（§10）。
好的一面是 同报告 §7 已独立证实腾讯批量报价的 `[4]` 与本节 `pre_close` 同口径（除权参考价），
所以"`pre_close` 不可当 raw 前收"这条结论对两条链路都成立。

当日快照的三层构成（`market_snapshot` join `stock_list`）：

## 2. 字段一致性对拍（全量 5,213 对，0 偏差）

```sql
-- 快照
SELECT stock_code, latest_price, open, high, low, pre_close, change_percent
FROM market_snapshot WHERE trade_date = '20261013';
-- 真值
SELECT stock_code, open, high, low, close, tradestatus, change_percent
FROM stock_daily WHERE adj='none' AND source='baostock' AND trade_date='20261013';
```

| 快照字段 | 对拍字段 | 对数 | 完全相同 | 一致率 | 最大绝对差 | 最大相对差 | ≤0.005 / ≤0.01 / ≤0.05 / >0.05 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| `latest_price` | `close` | 5,213 | **5,213** | **100%** | 0.000000 | 0 | 0 / 0 / 0 / 0 |
| `open` | `open` | 5,212 (+1 NULL) | **5,212** | **100%** | 0.000000 | 0 | 0 / 0 / 0 / 0 |
| `high` | `high` | 5,212 (+1 NULL) | **5,212** | **100%** | 0.000000 | 0 | 0 / 0 / 0 / 0 |
| `low` | `low` | 5,212 (+1 NULL) | **5,212** | **100%** | 0.000000 | 0 | 0 / 0 / 0 / 0 |

**偏差分布是退化的**：不是"99% 在 1 分钱内"，而是**一条偏差都没有**（中位数、P99、最大值
全为 0）。原因是两侧列都是 PostgreSQL `real`（float4），两个源报的同一个十进制价被解析成
同一个 4 字节浮点；任何"取整到分"的差异、任何前复权污染都会立刻现形。因此这张表**没有
可列的量级异常**——只有"整行为 NULL"这一类结构性异常。

异常清单（5 类；其中行级异常共 **362 行**——361 只 NULL 价 + 1 只 NULL OHLC，其余 3 类是全表级缺口，全在快照侧）：

| 类别 | 行数 | 明细 | 处理 |
| --- | ---: | --- | --- |
| 快照 `latest_price` 为 NULL | 361 | 343 死码 + 12 停牌 + 6 未上市（§1） | 不能写进 raw 表；按 §3 特征剔除 |
| 有价但 OHLC 全 NULL | **1** | `688496 *ST清越`：`latest_price`=0.58、`open/high/low`=NULL、`volume/amount`=NULL、`change_percent`=0.0；baostock 侧 `O=H=L=C=0.58`、`tradestatus=0` | 唯一"有价无成交"行；OHLC 对拍的 1 个 NULL 对就是它 |
| `amplitude` 全 NULL | 5,923 | 该源从未填过此列（腾讯适配器会填 `[43]`） | 不能用快照出振幅 |
| `pb_ratio` 全 NULL | 5,923 | 同上（腾讯适配器会填 `[46]`） | 不能用快照出市净率 |
| `volume_ratio` 为 NULL | 363 | 361 NULL 价行 + 2 只有价行：`688496 *ST清越`（停牌，无量）与 `301660 N粤芯-U`（上市首日，无 5 日均量可算） | 量比对新股/停牌不可用 |

**12 只停牌 + 6 只"当日尚未上市"** 构成 `stock_list.source='akshare'` 侧的 18 只 NULL 价行。
后者是：`301569 联亚药业`（库内首行 2026-10-15）、`301718 通则康威`（首行 10-22）、
`920162/920196/920285/920296`（首行 10-15/10-16/10-23/10-21）。它们**有 `pre_close` 但从未
成交过**，那个 `pre_close` 是发行/参考价性质——写进 raw 表就会凭空造出一根 bar（§4 P3 反证）。

**两种源对"停牌"的表达是相反的，而且各有一半是假话：**

| 观察 | baostock（`adj='none'`） | market_snapshot（efinance） |
| --- | --- | --- |
| 行 | 在 | 在 |
| 价格 | **合成平盘 bar**（`O=H=L=C=前收`）——看起来像"当天不涨不跌地成交了" | **NULL**（12/13）——诚实地表示"当天没有价格" |
| 成交量/额 | NULL | NULL |
| 标记 | `tradestatus=0`（唯一的"这是停牌"信号） | **无任何标记**，只能靠"价 NULL"间接推 |

所以：

1. **"停牌"可从快照识别**，判据是 `latest_price IS NULL AND pre_close IS NOT NULL AND volume IS NULL`，
   `pre_close` 就是停牌前最后收盘（13/13 与 baostock 当日 close 相同）。
2. **"无数据"与"停牌"可区分**：整行缺失 = 不在采集域（§6 的 `920306`）；行在但价 NULL =
   当日不产生价格。
3. **但"价格 NULL"不等于"停牌"**：361 只 NULL 价里只有 **12 只**是停牌，另外 **343 只**
   是已退市/特殊品种（上游夹带，§1）、**6 只**是尚未上市。**必须用 `stock_list` + 历史最末日
   才能把三种原因分开**——快照自己不带这个信息。
4. 反过来，**要判断"某只票某天是停牌还是真平盘"，baostock 的 `tradestatus` 是唯一权威**；
   快照的 NULL 更干净但不解释原因（688496 就既像停牌又像正常 0 成交）。

## 5. 收盘稳定性：写入时点可回溯，请求时点不可回溯

| 证据 | 值 |
| --- | --- |
| 5,923 行 `created_at` | **全部 = `2026-10-13 16:15:54.371644`**（同一事务批量 `execute_values`） |
| 同一次运行写 `stock_list` | `2026-10-13 16:15:52.522140`（343 行 `source='efinance'`）→ 快照紧随其后 **1.85s** |
| A 股收盘 | 15:00:00 → 写入 **+75 分 54 秒** |
| `collection_log`（`trade_date='20261013' AND section='market_snapshot'`） | **0 行**。台账最早一行 `2026-10-19 09:55:57`，比事件晚 6 天 → **那次运行没有留下台账** |
| 上游请求时刻 / 上游数据截止时刻 | **未验证**（无台账、无上游时间戳落库） |

`created_at` 的语义可以从代码确认（`repository.py:152-169`）：它在 `template` 里以
`CURRENT_TIMESTAMP` 写在**最后一位**，且 `ON CONFLICT DO UPDATE` 的 `updates` 列表只含
`SNAPSHOT_FIELDS`（不含 `created_at`）→ **`created_at` 是首次插入时间，后续 upsert 不会刷新它**。
本次 5,923 行时间戳完全一致，说明这一天只被写过一次、没有被次日/后续重跑覆盖。

**"是不是收盘后的最终值"不能靠台账，只能反证**：`high`/`low` 这种日内极值如果采集于盘中，
几乎不可能与收盘后的定稿 bar 逐位相同。实测 **`high` 5,212/5,212、`low` 5,212/5,212 完全相同**，
说明采集时刻晚于当日最后一笔成交——即 **16:15 这份快照确实是收盘定稿**。这条反证比时间戳更强，
因为时间戳只证明"什么时候写库"，不证明"写进去的是不是最终值"。

**但"能不能补历史"是另一回事**：`fetch_market_snapshot(date)` 有服务端日期防线
（`tools_snapshot.py:100-120`，`date_mismatch` 直接拒绝落库），端点本身也只有"当前快照"
一个语义 → **漏跑一天就永久缺失，无法回补**。

## 6. 覆盖率：5,923 / 5,924，唯一缺码是事后才上市的

| 集合 | 行数 |
| --- | ---: |
| `market_snapshot`（20261013） | **5,923** |
| `stock_list`（2026-10-30 最新态） | **5,924** |
| 快照有而清单无 | **0** |
| 清单有而快照无 | **1** → `920306 天元重工` |

`920306` 的判定证据：`stock_list.updated_at = 2026-10-30 21:14:57`，`source='akshare'`；
`stock_daily`（含 `qfq/efinance` 1990-12-19..2026-10-13 全历史、`qfq/tencent`
2026-06-12..2026-10-30）**零行**，`market_snapshot` **零行** → 它是 10-30 前后才上市的，
10-13 当然不该有。**因此 10-13 当日的可选域覆盖是 100%**。

两个必须写明的口径问题：

1. **这份快照不是清单驱动的**（efinance `get_realtime_quotes` 一次全市场），所以它把上游
   的 343 只死码也带了进来（§1）。覆盖率"高"部分来自"上游给什么就存什么"。
   **当前腾讯链路是清单驱动的**（`_snapshot_codes` → `stock_list` 兜底），其覆盖率口径会变成
   "`stock_list` 有多少就请求多少"，与本节不可直接互换。
2. **`stock_list` 自身在膨胀**：`collection_log` 记 2026-10-30 那次 `rows=5577`，表里却有
   5,924 行 → 历史行只增不删，343 只死码永久滞留（也因此本次快照能与清单 1:1 对上）。
   用 `stock_list` 当"当日可选域"时，必须再叠一层"当日有价/有历史末行"的过滤。

## 8. 单位与字段缺口（作 raw 源的硬约束）

| 列 | 10-13 快照（efinance） | 当前腾讯适配器会写的 | 冲突 |
| --- | --- | --- | --- |
| `volume` | **手**（对 baostock 股数恒为 0.01，含科创板） | **股**（`手 × 100`，科创板原生股，ADR 0008） | **同一张表两种单位**；#79 的 `migrate_volume` 一次性迁移尚未覆盖 10-13 这批 `source='efinance'` 行 |
| `amount` | 万元（ADR 0006 口径） | 万元 | 一致 |
| `market_cap`/`float_cap` | 万元 | 万元 | 一致 |
| `amplitude` | **全 NULL** | 有值（`[43]`） | 该源不产出 |
| `pb_ratio` | **全 NULL** | 有值（`[46]`） | 该源不产出 |
| `volume_ratio` | 363 NULL | 有值（`[49]`） | 部分缺 |
| `source` | 有（`efinance`） | `tencent`/`sina` | 可用于单位判别 |

**"收盘后 1 次批量报价"这个说法本身也要打折**：腾讯快照适配器按 `QT_BATCH_SIZE=80` 分批，
全市场 5,924 只需 **⌈5924/80⌉ = 75 次请求/轮**（`tencent_adapter.py:93` 注释记"5576 只实测
70 请求/轮"），批间 `QT_BATCH_PAUSE_S=0.1`；#150 已实测"362 只 1 次请求"可行（169 KB、
2.53 s），但**全市场单请求**（URL ~50 KB）仍未验证。所以现实成本是 **~70–75 次/日**，
不是 1 次——仍然便宜（相对逐只 5,924 次），但不是"一次"。

## 9. 结论：能作什么、不能作什么

### 9.1 能作（有实测支撑）

| 用途 | 依据 | 附加条件 |
| --- | --- | --- |
| **当日不复权 OHLC 的补充/核对源** | 沪深 5,213/5,213 四价全等（§2）；北交所 2/2 全等（§4） | 只在"当日、收盘后采集"成立；必须剔除 NULL 价行 |
| **当日全市场覆盖度盘查** | 5,923/5,924，含 349 只 BSE（baostock 完全没有） | 对应"efinance 版"；腾讯版是清单驱动，§6 口径要重算 |
| **停牌"当日无价格"的事实记录** | 13/13 与 baostock `tradestatus=0` 对得上（§3） | 只给"有没有价"，不给"为什么没价" |
| **北交所当日 raw 的唯一库内来源** | baostock 无 BSE；库内无其他 BSE 日线源 | 仅 1 天，不能回补 |

### 9.2 不能作（明确排除）

| 用途 | 原因 |
| --- | --- |
| **`pre_close` / `change_percent` 当 raw 前收/raw 涨跌幅** | 除权日 = 除权参考价（17/17 例，§7）；直接写进 raw 会造出"凭空 −27% 的假跌幅" |
| **历史回补 / 任意历史日** | 库内只有 2026-10-13 一天；端点只服务"当前快照"，`date_mismatch` 防线拒绝按日补抓；漏跑不可补（§5） |
| **"T+0 当日因子探测"的独立依据** | 除权因子只能靠 `pre_close ÷ 自身存的 D−1 收盘` 反推，**前提是你自己已经存了 D−1**；漏一天即断链（同报告 §5） |
| **振幅 / 市净率 / 可靠的量比** | `amplitude`、`pb_ratio` 全 NULL（§8） |
| **直接混用的成交量** | `volume` 手/股混源（§8），未跑 #79 迁移前不可跨源求和 |

### 9.3 必须回落 baostock / 腾讯 K 线的场景

| 场景 | 回落目标 | 理由 |
| --- | --- | --- |
| 任意历史日的 raw 日线（沪深） | `stock_daily adj='none' source='baostock'` | 唯一有全窗口 raw 的库内源 |
| 任意历史日的 raw 日线（北交所） | 腾讯 K 线 `day`（不复权） | baostock 无 BSE |
| 判断某日是否停牌 | baostock `tradestatus` | 快照无停牌标记，只有 NULL（§3） |
| 除权因子 / 除权事件 | baostock 复权因子；腾讯 `day` 行内 `djr/cqr/FHcontent` 元数据（仅沪深，见该报告 §7） | 快照的 `pre_close` 只能反推"当天有没有事"，不能给因子历史 |
| 需要 ≥2 天连续序列的任何计算 | 以上两者，不要用快照 | 快照只有一天 |

**一句话给下游**：把 `market_snapshot` 当"当日收盘 OHLC 的一次快照副本"用（并只用
`latest_price/open/high/low` 四列 + `stock_code` + `trade_date`），`pre_close`、
`change_percent`、`volume` 三列在跨源使用前必须先过口径判定；任何跨日、任何回补、
任何因子序列，一律回落 baostock（沪深）/ 腾讯 K 线（北交所）。

## 10. 未验证 / 待验证

1. **腾讯链路自身的快照行为未验证**（最重要）。库内唯一一天是 efinance 写的，而 efinance
   已退役。腾讯适配器会填 `amplitude`/`pb_ratio`、`volume` 是股、对停牌/死码可能返回
   **冻结价而不是 NULL**（同报告 §3 实测 6 只冻结行）。**验证方法**：连续 2 个交易日收盘后
   各跑 1 次 `fetch_market_snapshot`，用次日 `adj='none'` 真值对拍同一套脚本（0 次网络额外成本）。
2. **上游请求时刻**未验证（无 `collection_log`）。`created_at` 只证明写库时刻，§5 的
   "收盘后定稿"是靠 high/low 全等反证的。下一次采集若留下台账，可直接读 `started_at`。
3. **`volume_ratio` 的 2 只 NULL 有价行**已查明为 `688496 *ST清越`（停牌）与
   `301660 N粤芯-U`（上市首日无均量），语义自洽；但"新股首日量比"在腾讯链路下会填什么值
   未实测。
4. **全市场单次批量报价上限**未探边界：362 只/1 次已知可行，5,924 只/1 次（URL ~50 KB、
   响应 ~2.3 MB）**未测**；若可行，快照成本可从 75 次降到 1 次。
5. **`pre_close` 对"非除权类"事件的形态**未验证（如缩股、并购换股），样本里只有分红/送转。
6. **本报告未评估**"用快照做因子探测"的精度：`pre_close ÷ 自存 D−1 收盘` 只在"除权日当天
   `pre_close` 被替换"成立时才有信号，非除权日恒为 1.000，无法区分"无事件"与"上游没回填"。
